# CAATSM Dashboard Troubleshooting Guide

This guide helps you find and fix common issues in the CAATSM Dashboard stack. Follow the sections in order: start with health checks, then dig into specific systems, and finish with environment resets if needed.

---

## 1. Quick Health Snapshot

Run these commands from the project root to verify that the core services are alive:

```bash
curl -f http://localhost:3002/api/health
curl -f http://localhost:7700/health
redis-cli ping
nats server check
psql "$CAATSM_DATABASE_DSN" -c "SELECT 1"
task dev:logs
```

If any command fails, jump to the matching section below.

---

## 2. Backend Not Running

**Symptoms**

- `curl` to `/api/health` fails or returns `connection refused`.
- Logs show build or config errors.

**Checks**

1. Run `make dev` in a dedicated terminal.
2. Watch the log output to confirm “server listening on”.

```bash
make dev
# In another terminal:
tail -f logs/backend.log
```

3. If the process exits immediately, check the configuration validation messages. They point to missing TLS, auth, or DSN settings.

---

## 3. Database Issues (PostgreSQL / TimescaleDB)

**Symptoms**

- API returns 500 errors mentioning `pgx`.
- Health check reports `database: degraded`.
- Queries time out or pool exhaustion appears in logs.

**Diagnostics**

```bash
make dev-up
psql "$CAATSM_DATABASE_DSN" -c "SELECT version();"
psql "$CAATSM_DATABASE_DSN" -c "SELECT COUNT(*) FROM telegrams;"
psql "$CAATSM_DATABASE_DSN" -c "SELECT * FROM pg_stat_activity;"
```

**Fixes**

- Confirm DSN settings in `.env.local` or the active config file.
- Ensure migrations ran: `task migrate`.
- Increase connection limits only after verifying query load; defaults handle development.

## 4. Meilisearch Problems

**Symptoms**

- Search returns no results or stale data.
- Health endpoint says `meilisearch: degraded`.
- Logs show “connection refused” or “unauthorized”.

**Steps**

```bash
curl -f http://localhost:7700/health
curl -f http://localhost:7700/indexes/telegrams/stats
curl -f -H "Authorization: Bearer $CAATSM_MEILISEARCH_API_KEY" \
  http://localhost:7700/indexes/telegrams/search?q=test
```

**Resolutions**

- Verify the API key matches the one generated by Meilisearch.
- If the index is missing, delete and rebuild: stop the dashboard, run `curl -X DELETE http://localhost:7700/indexes/telegrams`, restart the backend to recreate and rehydrate it.

---

## 5. Redis/Valkey Cache and Event Bus

**Symptoms**

- Stats lag behind live data.
- Health endpoint reports Redis degraded.
- WebSocket disconnect messages mention “slow client” or “publish error”.

**Troubleshooting**

```bash
redis-cli -u "$CAATSM_REDIS_ADDR" ping
redis-cli monitor
task dev:logs
```

**Corrective Actions**

- Confirm credentials and TLS settings.
- Slow clients: increase `websocket.client_buffer_size` or review frontend consumption logic.
- Restart the cache container if it is unresponsive: `docker compose -f docker-compose.dev.yml restart redis`.

---

## 6. NATS Streaming Issues

**Symptoms**

- Live feed shows no new telegrams.
- Sync worker logs `JetStream disconnected`.
- Health endpoint marks NATS as degraded.

**Steps**

```bash
nats server check
nats stream info telegrams
nats consumer info telegrams dashboard-sync
task publish-stream:fast
```

**Fixes**

- Ensure the sync worker is running: `make dev` (backend) plus `task sync`.
- Recreate the stream if IDs changed: `nats stream create --config deploy/nats/telegrams.json`.

---

## 7. WebSocket Failures

**Symptoms**

- Frontend reports “Unable to connect to live stream”.
- Frequent reconnect attempts visible in browser console.

**Work Plan**

1. Open browser dev tools → Network → WS → observe connection status.
2. Check backend logs for “websocket hub” messages.
3. Inspect metrics:

```bash
curl http://localhost:3002/metrics | grep websocket
curl http://localhost:3002/metrics | grep backpressure
```

**Resolutions**

- Adjust allowed origins in config if the frontend runs on a different host.
- If buffers overflow, either consume messages faster on the client or increase buffer size in configuration.
- Restart the backend to clear stuck sessions.

---

## 8. Frontend Build and Dev Server Issues

**Symptoms**

- `npm run dev` or `deno task dev` fails.
- Hot reload stops working.

**Checklist**

```bash
cd frontend
deno cache --reload
npm install        # only if using Node.js
npm run check      # or deno task check
npm run lint       # or deno lint
npm run dev        # or deno task dev
```

**Additional Tips**

- Delete `.svelte-kit/` and rerun the build if type generation fails.
- Ensure the dev server proxy still targets `http://localhost:3002`.

---

## 9. Rate Limiting and 429 Errors

**Symptoms**

- API returns `429 Too Many Requests`.
- Health check still passes.

**Actions**

- Confirm request rate from scripts; back off if you exceed limits.
- Adjust `rate_limit_requests` and `rate_limit_burst` in config for controlled environments.
- Ensure automated jobs throttle requests.

---

## 10. Configuration Validation Failures

**Symptoms**

- Backend exits on startup with “config validation failed”.

**Resolutions**

1. Review the error list printed to the console; it names the missing or invalid fields.
2. Double-check environment variables and config files.
3. For production mode:
   - TLS must be enabled.
   - Default API keys like `masterKey` are rejected.
   - Authentication must be active.

---

## 11. Resetting the Local Environment

If multiple services are failing or data is inconsistent:

```bash
make dev-down
docker compose -f docker-compose.dev.yml down -v
docker compose -f docker-compose.dev.yml up -d
task migrate
task generate-test-data
task publish-stream:fast
```

After reset, rerun the quick health snapshot in Section 1.

---

## 12. Collecting Evidence for Support

When escalating an issue:

1. Capture logs (`logs/backend.log`, `docker compose logs`).
2. Export relevant metrics or screenshots of dashboards.
3. Include configuration snippets without revealing secrets.
4. List reproduction steps with exact commands.

Share this bundle through the secure channel defined by your team.

---

Staying systematic—checking health, isolating the failing subsystem, and validating configuration—resolves most issues quickly. Keep this guide updated as new failure modes appear.
